# RideShare Interview Questions and Answers

## Project and architecture

### 1. Explain the project in two minutes.

RideShare connects passengers with drivers already travelling by motorbike. Drivers publish scheduled routes. Passengers search by pickup, destination, date, and time. Nominatim geocodes addresses, OSRM calculates routes, and the backend checks ordered proximity between passenger endpoints and the driver's stored route path. A booking creates a passenger request, updates the driver's route, and emails the driver. JWT cookies and role middleware protect user and driver operations.

### 2. Why did you separate frontend and backend?

The React frontend handles UI and navigation, while Express exposes a clear API boundary for authentication, business rules, database access, and external services. This allows each layer to be deployed and scaled independently and prevents database credentials from reaching the browser.

### 3. Why MongoDB?

The data is naturally document-oriented: users and drivers have different profiles, and a route contains an ordered array of coordinates plus a matched-user subdocument. Mongoose adds schema validation, references, middleware, and convenient population. For a larger geospatial workload, MongoDB geospatial indexes or a dedicated spatial solution would be evaluated.

### 4. What is the most important business algorithm?

Partial-route matching. The driver route is an ordered array of latitude/longitude points. For each point, the server calculates Haversine distance to the passenger pickup and destination. Candidates within one kilometre are found, and the destination candidate must appear after the pickup candidate in the driver's route order.

### 5. What is the complexity of matching?

For one driver route with $p$ points, the check is $O(p)$. For $r$ candidate routes, the current implementation is approximately $O(\sum p_i)$ plus database lookups, because it reads all routes and scans them in application memory. It is not ideal for large scale. I would first filter by indexed date, status, and time, then use geospatial indexing or a route-search service.

## Authentication and security

### 6. How does JWT authentication work here?

At login, the server validates the password and signs a token containing the user ID and role. It places the token in an HTTP-only cookie. Middleware verifies the token on later requests and sets `req.user`. User and driver middleware then check the role before allowing protected operations.

### 7. Why use an HTTP-only cookie?

JavaScript cannot read an HTTP-only cookie, which reduces exposure to token theft through many XSS scenarios. The request still needs CSRF consideration because cookies are sent automatically. In production I would use HTTPS, `Secure`, an appropriate `SameSite` policy, CSRF protection where needed, short token expiry, refresh-token rotation, and a secret from a secret manager.

### 8. What security problems would you fix?

I would move the JWT secret out of source code, reject invalid-token verification errors instead of continuing, validate ownership before updating a route, use bcrypt or Argon2 consistently, avoid logging credentials or tokens, add rate limiting and request validation, and configure CORS with the deployed frontend origin rather than a fixed development origin.

### 9. Is the current password hashing ideal?

No. The model uses HMAC-SHA256 with a random salt, while password hashing should use an adaptive password-specific function such as bcrypt or Argon2. The `bcrypt` dependency is present but the model does not currently use it. I would migrate carefully: verify legacy passwords, rehash successful logins, and eventually remove the old scheme.

## HTTP, WebSockets, and asynchronous behavior

### 10. Does this project use WebSockets?

No. The repository has no WebSocket or Socket.IO dependency and no socket server. It uses HTTP requests for operations and Nodemailer for driver notification. The README's “real-time connection” is a product description, not an implemented persistent socket connection.

### 11. When would you use WebSockets here?

For live ride-request and status updates. The browser would authenticate during the WebSocket handshake, join a user or ride room, and receive events after MongoDB successfully changes state. HTTP would remain the fallback for initial state, refresh, retries, and reconnect recovery.

### 12. WebSocket versus HTTP?

HTTP is request/response and simple for CRUD and page loading. WebSockets maintain a persistent bidirectional connection and are better for low-latency server push. WebSockets add connection lifecycle, scaling, authorization, reconnection, and delivery-order concerns, so they should be added only where live updates provide value.

### 13. How are external API failures handled?

The map helper wraps external calls, validates coordinates, returns readable errors, and caches successful results in memory for ten minutes. A production version should add timeouts, retries with backoff, circuit breaking, provider quotas, and a durable or distributed cache if multiple backend instances are used.

## Database and consistency

### 14. Why use `populate`?

References such as `driverId`, `userId`, and `rideId` store IDs rather than duplicating profile documents. `populate` resolves related records for read responses, such as showing driver details in passenger history. It should be used carefully because excessive population can create slow or expensive queries.

### 15. What happens if booking creates the request but route update fails?

The current code performs separate operations, so a partial failure can leave inconsistent data. A production implementation should use a MongoDB transaction where supported, or an idempotent workflow with a request ID and recovery/reconciliation job.

### 16. How would you prevent two passengers from booking the same route?

Use an atomic conditional update such as updating only a route whose status is `available`, inspect the modified count, and create the passenger request within a transaction. A unique/idempotency key can prevent duplicate retries from creating multiple requests.

### 17. What indexes would you add?

At minimum, unique indexes already implied by schema fields should be verified. I would add a compound index for route search such as `{ status: 1, date: 1, rideStartTime: 1 }`, indexes on `userRoute.userId` and `route.driverId`, and evaluate a `2dsphere` representation if geospatial querying is introduced.

## Frontend

### 18. What does Redux store?

The current auth slice stores the selected user type and user ID. It is useful for UI decisions, but the server cookie remains the security authority. The frontend must never treat Redux state alone as proof of authorization.

### 19. Why debounce location autocomplete?

Without debouncing, every keystroke would call the geocoding provider. The UI waits briefly after typing, reducing request volume and improving usability. `mapApi.js` also caches results and reuses an in-flight request for identical queries.

### 20. How does frontend route protection work?

React Router loaders check authentication before rendering selected user or driver pages. This improves user experience, but it is not a security boundary. The backend middleware must enforce authorization on every protected API endpoint.

## Testing and production design

### 21. What would you test?

Unit tests for polyline decoding, Haversine distance, route-order matching, fare calculation, and state transitions. Integration tests for signup/login, role rejection, offer creation, booking, accept/decline, completion, and feedback. End-to-end tests would cover driver publish, passenger search, booking, and history.

### 22. What edge cases matter?

No geocoding result, external API timeout, identical pickup and destination, destination occurring before pickup, route exactly at the tolerance boundary, time-zone differences, duplicate booking clicks, expired cookies, invalid ObjectIds, a driver declining after the scheduled time, and two passengers racing to book one route.

### 23. How would you scale it?

Run stateless API instances behind a load balancer, use MongoDB Atlas with indexes, add a shared cache such as Redis, move email to a queue worker, rate-limit external map calls, paginate history and search results, and replace the full route scan with indexed geospatial matching. A WebSocket layer would need a shared adapter such as Redis for multi-instance event delivery.

### 24. How would you monitor it?

Structured logs with request IDs, metrics for API latency and map-provider failures, database query timing, booking conversion, email failures, and status-transition errors. Distributed tracing would connect a passenger request through Express, MongoDB, OSRM, and email work.

### 25. What would you improve first?

First, security and correctness: environment-based JWT keys, strict invalid-token handling, input validation, ownership checks, and atomic booking. Second, automated tests around the matching and state machine. Third, indexed route search and live status events.

## Rapid-fire concepts

- **Middleware:** a function that runs in the request pipeline before the handler.
- **Controller/handler:** application code that validates input, calls services/models, and builds the response.
- **ODM:** Mongoose maps JavaScript objects to MongoDB documents and provides schemas and hooks.
- **CORS:** browser policy that controls which origins may call the API; it is not authentication.
- **Cookie `credentials`:** frontend requests need credentials enabled for the browser to send the auth cookie cross-origin.
- **Geocoding:** address to coordinates.
- **Reverse geocoding:** coordinates to a readable address.
- **Polyline:** compact encoding of an ordered path made of coordinates.
- **Haversine distance:** spherical distance between two latitude/longitude points.
- **Idempotency:** repeating the same request does not create duplicate side effects.
- **Transaction:** a group of database operations that commit or roll back together.
- **Source of truth:** persisted ride state in MongoDB, not a browser screen or a WebSocket event.
