# Graphify Interview Guide

## 1. Thirty-second introduction

Graphify is a client-side algorithm visualizer built with React, Vite, and SVG. A user can create or edit graphs and binary trees, choose BFS, DFS, Dijkstra, or a tree traversal, generate a sequence of algorithm events, and play those events forward or backward. The project separates the data model, algorithm logic, playback state, and rendering so the same algorithm output can drive both the visualization and the execution-insights panel.

The current version is intentionally frontend-only. It has no API, database, authentication, or WebSocket server. Saved graphs use browser `localStorage`.

## 2. Project walkthrough

### Entry point

`src/main.jsx` mounts `<App />` inside React `StrictMode`.

### App orchestration

`src/App.jsx` owns the application state and coordinates:

- Current page: visualization or code viewer.
- Current mode: graph or tree.
- Graph/tree data.
- Selected algorithm, start node, and target node.
- Generated algorithm steps.
- Playback controls, canvas resizing, fullscreen, and modals.
- Graph editing and tree editing actions.

This is a reasonable small-project choice because `App` is the composition root. If the application grew, I would move graph editor state and execution state into separate reducers or contexts.

### Domain/model layer

- `src/lib/graphModel.js`: graph creation, mutation helpers, random/grid generation, and adjacency-list conversion.
- `src/lib/treeModel.js`: binary-tree creation, node insertion/removal, connection validation, and layout calculation.
- `src/lib/algorithms.js`: pure functions that convert a graph/tree into ordered visualization steps.
- `src/lib/stepState.js`: replays a prefix of the step list and derives the state visible at that point.

### UI layer

- `GraphCanvas.jsx`: interactive SVG graph, zoom/pan, node dragging, edge/node highlighting.
- `TreeCanvas.jsx`: SVG binary-tree renderer with computed layout and zoom/pan.
- `ControlPanel.jsx`: play, pause, previous, next, reset, and progress count.
- `Sidebar.jsx`: current event, visited order, queue/stack, distances, parents, path, and timeline.
- `CodeSnippetPage.jsx`: algorithm explanations and sample code in C++, Java, and Python.
- `TheoryPage.jsx`: short algorithm summaries.

## 3. Main runtime flow

1. The user edits a graph or tree.
2. The user chooses an algorithm and clicks **Generate Steps**.
3. `App.runSelectedAlgorithm()` calls a pure function such as `bfsSteps(graph, startNode, targetNode)`.
4. The algorithm returns event objects such as `visit`, `edge`, `enqueue`, `relax`, and `path`.
5. The events are stored in React state as `steps`.
6. `usePlayback(steps)` stores the current index and play/pause state.
7. `derivePlaybackState(steps, stepIndex)` replays all events before the current index.
8. `GraphCanvas`/`TreeCanvas` render colors and highlighted edges from the derived state.
9. `Sidebar` renders the same state as human-readable explanations and data tables.

The key design idea is that the algorithm does not manipulate the DOM. It produces a deterministic event log, and rendering is a projection of that log.

## 4. Algorithm details

### BFS

- Uses an adjacency list, a queue, a visited set, and a parent map.
- Marks a node visited when it is discovered/enqueued, preventing duplicate enqueues.
- Stops early when the target is dequeued/visited.
- Reconstructs a path using parent pointers.
- Complexity: $O(V + E)$ time and $O(V)$ auxiliary space.
- Shortest path guarantee applies to unweighted graphs, or graphs where every edge has equal cost.

### DFS

- Uses recursion and a visited set.
- Emits explicit `push`, `visit`, `edge`, `backtrack`, and `pop` events.
- The traversal order depends on the sorted adjacency-list order.
- Complexity: $O(V + E)$ time and $O(V)$ space, including recursion stack.

### Dijkstra

- Initializes every distance to infinity and the source to zero.
- Relaxes an edge when a shorter candidate distance is found.
- Stores a predecessor in `previous` for path reconstruction.
- The UI emits `pq-enqueue` and `pq-dequeue` events for educational purposes.
- Important implementation detail: `dijkstraSteps()` actually scans all unvisited distances to find the minimum; it does not use a heap. Therefore the current implementation is approximately $O(V^2 + E)$ time and $O(V + E)$ space.
- A true binary-heap implementation would be approximately $O((V+E)\log V)$ and should ignore stale heap entries when popped.
- Dijkstra requires non-negative edge weights. Negative weights require Bellman-Ford or another suitable algorithm.

### Tree traversals

The tree walker recursively follows `left` and `right` references:

- Inorder: left, root, right.
- Preorder: root, left, right.
- Postorder: left, right, root.

Each traversal is $O(n)$ time and $O(h)$ recursion space, where $h$ is tree height. The project stores a binary tree, but it does not enforce binary-search-tree ordering.

## 5. Why the step/event architecture is useful

A direct animation implementation would mix algorithm logic with timers and DOM updates. Graphify instead uses an event-sourcing-like approach:

```text
algorithm(input) -> immutable step[] -> replay prefix -> visual state
```

Benefits:

- Pause, resume, next, previous, and reset are simple index operations.
- The sidebar and canvas consume the same source of truth.
- Algorithm functions are easier to test without a browser.
- A recorded event list could later be sent over a network or persisted.
- The step descriptions make the algorithm explainable to a learner.

Trade-off: `derivePlaybackState` replays from the beginning whenever the index changes. This is simple and deterministic, but for very long runs a checkpoint system or incremental reducer would be more efficient.

## 6. State and persistence

React state is the source of truth during the session. Graph editing uses immutable updates: each model helper returns a new graph object, node array, or edge array instead of mutating the previous state.

The Save action serializes the graph to `localStorage` under `graphify_saved_graph`. Load parses it and restores the graph. This is local to one browser profile and is not collaborative or server-backed.

Important limitations to mention:

- Only the graph is saved, not the tree or playback session.
- Local storage is synchronous and has a small quota.
- Loaded JSON is parsed but not deeply schema-validated.
- There is no cross-device synchronization.

## 7. Rendering and interaction

The canvases use SVG rather than a canvas bitmap. SVG is useful here because individual nodes and edges need click handlers, labels, transitions, and semantic DOM elements.

Graph interaction includes:

- Add node by clicking the canvas.
- Drag nodes with pointer events.
- Add directed/undirected and weighted/unweighted edges.
- Delete nodes or edges.
- Zoom and pan.
- Start and target highlighting.

Pointer coordinates are transformed through the SVG screen matrix and then adjusted for pan and zoom before updating model coordinates.

## 8. WebSocket interview topic

### Does the current project use WebSockets?

No. The current project is a single-user, browser-only application. Algorithm execution occurs locally and no socket connection is opened.

### How would I add collaboration?

I would add a server that owns a room's canonical graph and broadcasts commands or events:

```text
Browser A --WebSocket command--> Collaboration server
Browser B <--WebSocket event----- Collaboration server
```

A message could look like:

```json
{
  "type": "graph.node.added",
  "roomId": "demo-42",
  "revision": 18,
  "payload": { "id": "8", "value": "8", "x": 300, "y": 180 }
}
```

The server should validate the command, assign a monotonically increasing revision, persist or publish the resulting event, and broadcast it to room members. Clients should apply events idempotently and request a snapshot if they detect a revision gap.

### WebSocket lifecycle

1. Client opens `wss://host/ws`.
2. Server authenticates the connection and joins it to a room.
3. Client sends a command such as `node.add`.
4. Server validates authorization and payload.
5. Server updates canonical state and assigns a revision.
6. Server broadcasts the accepted event.
7. Clients update local state and acknowledge or display errors.
8. Heartbeats detect dead connections; reconnect uses exponential backoff.

### WebSocket versus HTTP

- HTTP request/response is simple for CRUD and snapshots.
- WebSocket is useful when the server must push low-latency updates.
- WebSocket is stateful, so authentication expiry, reconnects, ordering, backpressure, and horizontal scaling need explicit handling.
- For collaborative editing, use server-assigned ordering and conflict handling. Do not trust client timestamps as the ordering mechanism.

### WebSocket versus SSE

SSE is one-way server-to-client streaming over HTTP. It is simpler when clients only receive updates and send commands with normal HTTP. WebSockets support two-way low-latency communication on one connection.

## 9. Strong interview answers

### Why React?

React fits the interface because the canvas, controls, and sidebar are reactive views of changing graph, tree, and playback state. Component boundaries keep rendering concerns separate from model and algorithm code.

### Why pure algorithm functions?

Pure functions are deterministic, easy to unit test, and independent of browser APIs. They can return both the algorithm result and educational events without knowing how the UI renders them.

### Why adjacency lists?

Graphs in this project are sparse and interactively edited. An adjacency list uses $O(V+E)$ space and makes neighbor traversal efficient. An adjacency matrix would use $O(V^2)$ space and is useful mainly when constant-time edge lookup is more important.

### How is immutability handled?

Model helpers use object and array spread plus `map`/`filter` to return new references. React can then detect updates reliably and avoid accidental mutation of previous state.

### How would you test it?

Test model invariants, algorithm event sequences, path reconstruction, disconnected graphs, duplicate edges, directed/undirected behavior, zero nodes, invalid weights, and playback boundaries. Add component tests for controls and a browser smoke test for add node -> generate -> play.

### What would you improve?

I would split `App` state into reducers/hooks, add schema validation for loaded data, implement a real heap for Dijkstra, add unit tests, save trees and sessions, and introduce a backend only if sharing or persistence across devices is required.
