# RideShare Interview Guide

## 1. One-minute project explanation

RideShare is a MERN-style ride-sharing platform for motorbike commuters. A driver publishes a scheduled route with a source, destination, date, and time. A passenger searches for a route and schedule. The backend geocodes both locations, obtains driving directions from OpenStreetMap Nominatim and OSRM, stores the driver's route geometry in MongoDB, and checks whether the passenger's pickup and drop-off points occur along the driver's path. If a compatible ride is found, the passenger can request it. The system stores the request, marks the driver's ride as pending, and sends an email notification to the driver. The driver can accept or decline the request, and both passenger and driver records are updated as the ride progresses to completion. JWT authentication in an HTTP-only cookie separates user and driver capabilities.

## 2. Problem and value

The application matches a passenger who needs only part of a journey with a driver who is already travelling that route. This can reduce travel cost and vehicle usage. The important business rule is partial-route matching, not merely matching identical addresses.

## 3. Technology stack

- Frontend: React 19, Vite, React Router, Redux Toolkit, Tailwind CSS, MapLibre GL, Fetch/Axios-style HTTP calls, React Toastify.
- Backend: Node.js, Express, Mongoose, JWT, cookie-parser, CORS, Nodemailer.
- Database: MongoDB.
- External services: Nominatim for geocoding and autocomplete, OSRM for driving routes and distances.
- Core computation: polyline decoding, Haversine distance, route intersection detection.

## 4. Architecture

The application is a two-tier web application with an external-services integration layer:

```text
React/Vite browser
    |
    | HTTP/JSON + cookie credentials
    v
Express API (port 5001)
    |-- authentication middleware and route handlers
    |-- Mongoose models
    |-- route matching computation
    |-- Nominatim and OSRM clients
    |-- Nodemailer notification
    v
MongoDB
```

The frontend owns presentation, form state, navigation, map interaction, and small client-side caches. Express owns validation, authentication, business workflows, external API calls, and persistence. MongoDB stores users, drivers, offered routes, passenger requests, and feedback.

## 5. Backend request flow

`Backend/index.js` creates the Express app, configures CORS, parses JSON and cookies, connects to MongoDB, and mounts route modules. The route modules delegate work to handler functions. Handlers call Mongoose models and external API helpers.

Main route groups:

| Prefix | Responsibility | Important endpoints |
|---|---|---|
| `/user` | Passenger account | `POST /signup`, `POST /login`, `GET /getuserdetails`, `POST /logout` |
| `/driver` | Driver account | `POST /signup`, `POST /login`, `GET /profile`, `POST /logout` |
| `/offer` | Driver ride lifecycle | `POST /postride`, `GET /getridedetails`, accept/decline updates |
| `/book` | Passenger ride lifecycle | `POST /search`, `POST /matchride`, history, completion, feedback |
| `/maps` | Location and route services | `GET /search`, `GET /reverse`, `POST /route` |
| `/gettokendetails` | Token-related endpoint | `GET /get-token` |

## 6. Driver journey

1. Driver submits registration data and vehicle/license information.
2. The driver model hashes the password before saving and assigns role `driver`.
3. Login validates the password and signs a JWT containing `userId` and `role`.
4. The JWT is returned as an HTTP-only `token` cookie.
5. The protected offer route reads the cookie and requires the `driver` role.
6. The backend geocodes source and destination through Nominatim.
7. It asks OSRM for a driving route, distance, duration, and geometry.
8. The encoded route is decoded into latitude/longitude points and saved in `routePath`.
9. The route is stored as `available`.

## 7. Passenger journey

1. Passenger enters pickup, destination, date, and time.
2. The frontend uses debounced autocomplete and the map preview helpers.
3. `POST /book/search` geocodes the requested locations and gets the passenger route.
4. The backend calculates a fixed fare from the route distance.
5. It scans available driver routes with the same date and a suitable start time.
6. The intersection algorithm checks whether the passenger pickup and destination are near the driver's ordered route points.
7. Matching rides are returned to the results page.
8. On booking, `userRoute` is created with status `requested`.
9. The selected driver route is updated to `pending`, with references to the passenger and request.
10. Nodemailer sends the driver an email containing passenger and ride details.

## 8. Ride state lifecycle

Passenger request states are represented by `userRoute.status`:

```text
requested -> accepted -> completed
     |
     +-------> declined
```

The driver route also keeps a `matchedUser` subdocument containing the passenger ID, passenger-request ID, and request status. Accepting changes the driver route to `ongoing` and the passenger request to `accepted`. Declining either makes the route available again or cancels it depending on its date/time, and marks the passenger request declined. Completion updates both sides to `completed`.

## 9. Authentication and authorization

Authentication is cookie-based JWT authentication:

- Login signs a token containing the database ID and role.
- The browser sends the cookie when requests use `credentials: include`.
- General middleware attempts to attach the decoded payload to `req.user`.
- User middleware requires a valid token with role `user`.
- Driver middleware requires a valid token with role `driver`.
- The frontend also protects selected routes with React Router loaders.

In an interview, describe this as stateless server authentication: the server does not need a session table for each login; it validates the signed token on each request.

## 10. Mapping and matching

Nominatim converts text addresses into coordinates. OSRM calculates a driving route. The route is represented as an ordered series of coordinates. The backend decodes the encoded polyline before storing it.

The matching algorithm:

1. Iterate through each point in the driver's route.
2. Calculate Haversine distance from that point to the passenger pickup and destination.
3. Treat points within the one-kilometre tolerance as candidates.
4. Choose the closest pickup candidate.
5. Choose a destination candidate whose index is later in the route.
6. A ride matches only when both candidates exist in the correct order.

This prevents a route that passes near the two places in the wrong order from being accepted.

## 11. Frontend architecture

`main.jsx` creates the browser router and Redux provider. Routes render page components such as `OfferRide`, `SearchRidePage`, dashboards, profiles, and history pages. `Layout` provides shared navigation, footer, back-button behavior, and toast notifications. `authSlice` stores the current role and user ID for client UI decisions. `mapApi.js` centralizes map calls and maintains short-lived caches plus in-flight request de-duplication.

## 12. Honest limitations to mention

- There is no WebSocket or Socket.IO implementation in the current repository. Ride notifications are HTTP-driven and email-driven; “real-time” should be described as a product goal, not as an implemented WebSocket feature.
- Ride search currently reads all routes and performs matching in application memory. At scale, route filtering, geospatial indexes, pagination, and a spatial database strategy would be needed.
- JWT signing currently uses a hardcoded secret in `Services/Authentication.js`; production should use a strong environment variable and key rotation.
- Authentication middleware logs token verification errors and can continue to the handler. Invalid tokens should be rejected with `401` instead.
- The model uses a custom HMAC password scheme. A production system should use a password-specific adaptive hash such as bcrypt or Argon2 consistently.
- Booking and route updates are separate database operations. A transaction or idempotency strategy would reduce inconsistent states during failures.
- Search and some read operations are intentionally public in the current routing; production authorization and rate limiting should be reviewed endpoint by endpoint.

## 13. Strong closing statement

The strongest technical part of the project is the route-aware matching flow: it combines geocoding, routing, decoded path geometry, ordered intersection checks, MongoDB references, and a multi-step ride state machine. The main next step for production scale would be to harden authentication and consistency, then replace the in-memory route scan with indexed geospatial matching and add WebSocket or push notifications for request-status changes.
